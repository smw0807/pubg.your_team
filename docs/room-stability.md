# 2단계: 팀·채팅 안정화

## 변경 내용

- 방 직접 접속/새로고침에서 Firebase `authStateReady()`를 기다린 뒤 입장한다.
- 입장 트랜잭션은 본인 자리와 접속 신호를 함께 기록한다. 재입장해도 자리를 중복 추가하지 않는다.
- `onUnmounted`에서 비동기 퇴장을 시작하던 방식을 제거했다. 명시적 퇴장, 뒤로가기, 메뉴 이동, 방 간 이동은 라우트 가드에서 퇴장을 완료한 뒤 이동한다. 명시적 퇴장은 해당 플랫폼 목록으로 이동하므로 직접 링크로 접속해도 외부 사이트로 돌아가지 않는다.
- 확인 모달은 비동기 작업이 끝날 때까지 중복 클릭/닫기를 막고, 실패 시 재시도할 수 있다. 방에서 로그아웃할 때도 먼저 퇴장을 시도한다. 네트워크 오류로 퇴장이 실패해도 로컬 로그아웃은 막지 않으며 별도 안내를 표시한다.
- 실시간 구독 오류 콜백, 오프라인 안내, 수동 재연결, 연결 복구 시 재구독을 추가했다. 오래된 프로필 조회 결과가 최신 팀원 목록을 덮어쓰지 않도록 요청 버전을 확인한다.
- 여러 탭은 동일 UID의 자리 하나를 공유한다. 한 탭에서 명시적으로 퇴장하면 다른 탭도 참여 해제를 감지한다. 브라우저 강제 종료 시 비동기 쓰기가 완료된다고 가정하지 않는다.

## 접속 신호와 서버 정리

- `TEAMS/{teamId}/PRESENCE/{uid}`에는 `lastSeen` 서버 시각만 저장한다. 팀원 본인만 자신의 접속 신호를 갱신할 수 있다. 다른 사용자의 활동 정보는 공개하지 않는다.
- 방에 있는 동안 60초마다 갱신한다. 탭이 다시 보이거나 인터넷이 복구되면 즉시 갱신한다.
- 서버 정리는 마지막 접속 신호가 10분 이상 지난 회원만 제거한다. 접속 신호가 없는 구버전 회원은 보호한다. 오래된 방 전체를 생성일만 보고 삭제하지 않는다.
- 마지막 회원이 만료되면 먼저 방을 닫은 뒤 메시지/접속 정보/부모 방 순으로 정리한다. 이미 닫힌 방의 중단된 정리도 재개한다. 프로필이나 다른 컬렉션은 삭제하지 않는다.
- 접속 신호를 트랜잭션 안에서 다시 읽으므로 정리 중 새 접속 신호가 들어오면 재판단한다.
- 한 번에 최대 100개 방과 1000개 하위 정리 문서를 처리하고, 20초 작업 예산을 적용한다. 만료 회원의 접속 문서 삭제는 별도이며 최대 400개다. 커서를 `_SYSTEM/roomCleanup`에 저장하고 작업 잠금으로 중복 실행을 방지한다. 미완료 방은 다음 실행에서 이어서 처리한다.
- 많은 방이 있으면 한 번의 순회에 여러 실행이 필요하다. 10분은 삭제 시각 보장이 아니라 만료 판단 기준이다. 절전/백그라운드 정지 상태도 접속 신호가 끊길 수 있으므로 실제 사용 패턴을 보고 유예 시간을 조정한다.

## 운영 적용 (아직 적용하지 않음)

기존 1단계 운영 규칙은 `PRESENCE` 쓰기를 허용하지 않는다. **앱보다 새 규칙을 먼저 배포**해야 한다. 새 규칙은 기존 1단계 앱의 팀 생성/입퇴장도 계속 허용한다.

1. 테스트를 실행하고 현재 운영 규칙을 백업한다.
2. `yarn firebase deploy --only firestore:rules --project pubg-your-team`로 추가 규칙을 배포한다.
3. 새 앱을 배포한다. 서버 정리는 기본 비활성 상태여도 팀 기능과 접속 신호는 동작한다.
4. 서버 정리를 활성화하려면 Vercel의 서버 환경변수에 다음을 설정한다.
   - `FIREBASE_ADMIN_PROJECT_ID=pubg-your-team`
   - `CRON_SECRET`: 32자 이상 충분히 무작위인 비밀값
   - `FIREBASE_ADMIN_CLIENT_EMAIL`, `FIREBASE_ADMIN_PRIVATE_KEY`: 해당 프로젝트의 Firestore 읽기/쓰기 권한을 가진 전용 서비스 계정. 관리형 ADC가 있다면 두 값은 생략한다. 서비스 계정 키를 저장소나 브라우저에 넣지 않는다.
   - `ROOM_CLEANUP_ENABLED=true`: 인증 및 대상 프로젝트 검증 후 마지막에 활성화한다.
5. 스케줄 실행 주기와 요금제를 확인한 뒤 기존 `vercel.json`에 아래 설정을 병합하고 재배포한다. 이번 단계에서는 스케줄을 등록하지 않았다.

```json
{
  "crons": [{ "path": "/api/internal/rooms/cleanup", "schedule": "*/5 * * * *" }]
}
```

정리 API는 비활성 시 503, 잘못된 인증 시 401을 반환한다. Vercel은 `CRON_SECRET`을 Bearer 헤더로 보낸다. 실제 인증정보나 토큰을 응답에 포함하지 않는다. 관리자는 별도 준비 없이 임의의 `--apply`를 실행하는 대신, 먼저 에뮬레이터 검증과 운영 권한/대상을 확인해야 한다.

접속 신호는 방에 연결된 탭당 대략 분당 1회 쓰기를 추가한다. 서버 순회도 방/접속 정보 읽기와 만료 데이터 삭제 비용을 발생시킨다. Vercel 스케줄 사용 조건과 Firestore 사용량을 확인하고 활성화한다.

공식 참고: [Firebase 인증](https://firebase.google.com/docs/reference/js/auth.auth#authauthstateready), [Firestore 접속 상태](https://firebase.google.com/docs/firestore/solutions/presence), [Vercel Cron 관리](https://vercel.com/docs/cron-jobs/manage-cron-jobs).

## 검증 방법

```sh
yarn install --frozen-lockfile
yarn lint
yarn typecheck
yarn test
yarn build
yarn test:smoke
```

테스트는 `demo-` 프로젝트와 로컬 에뮬레이터에만 데이터를 만든다. 두 개의 독립된 인증 컨텍스트로 실제 클라이언트 입퇴장 서비스, 채팅 읽기 권한, 정원 경쟁, 새로고침 후 재입장, 다중 배치 정리를 검사한다. 서버 테스트는 새 접속 보호, 구버전 회원 보호, 부분 정리 재개, 커서 순회, 중복 실행 잠금, 잘못된 인증 거절을 검사한다. 운영 두 Google 계정의 브라우저 검증과 자동 정리 활성화는 배포 시 별도로 수행한다.

### 로컬 브라우저 검증 기록 (2026-09-13)

- 최종 자동 검사: 테스트 32개 통과, 린트/타입 검사/프로덕션 빌드 통과, HTTP smoke 검사 11개 통과.
- 기존 500kB 초과 클라이언트 번들 경고와 에뮬레이터 Admin SDK의 메타데이터 조회 경고는 남아 있다. 검사 실패는 없었다.

운영 DB와 분리된 `demo-pubg-ui` Auth/Firestore 에뮬레이터를 사용했다. 테스트 설정은 Git에서 제외되는 `.firebase/stage2-ui` Nuxt 레이어로만 주입했고, 운영 Firebase/Google 로그인은 사용하지 않았다.

- 방 생성 → 새로고침 → 인증 복원 → 중복 자리 없이 재입장 → 채팅 전송을 확인했다.
- 명시적 퇴장 후 카카오 목록으로 이동했고, 새로고침 없이 삭제된 카드가 사라진 것을 확인했다.
- 에뮬레이터에서만 팀 수정 권한을 일시 거절하여 퇴장 실패를 재현했다. 실패 안내와 확인창이 유지됐으며, 규칙 복구 후 확인 버튼 재시도로 정상 퇴장했다.
- 방 안에서 로그아웃하면 팀을 정리한 뒤 로그아웃 안내와 올바른 플랫폼 목록 링크가 표시됐다.
- 테스트 종료 시 방/채팅/접속 문서가 모두 0개임을 확인했다. 로컬 검증 서버는 종료했다.
