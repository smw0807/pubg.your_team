# 4단계: 전적 조회 안정화

## 계산 정확도

- 이전 API는 경쟁전 경기 수에 일반전 데미지/어시스트/다운 등을 섞어서 반환했다. 평균 딜량도 서로 다른 경기 집합의 분자/분모로 계산되었다.
- `/api/stats/rank`는 이제 경쟁전 응답만 사용한다. 일반전 조회 요청 자체를 제거했다. 현재 시즌 듀오/스쿼드 기록을 TPP/FPP별로 구분하고, FPP를 TPP 대체값으로 합치지 않는다.
- 평균 딜량은 동일한 경쟁전 모드의 `damageDealt / roundsPlayed`, K/D는 해당 모드의 `kdr`을 사용한다. SDK 타입에 없는 추가 필드는 런타임에서 숫자 여부를 검증한다. 필드가 없거나 유효하지 않으면 `null`/`—`로 표시하며 일반전 숫자나 0으로 채우지 않는다.
- 0경기 모드/빈 모드 맵은 기록 없음으로 처리한다. 응답 구조 자체가 잘못되면 502로 구분한다. 누락된 티어/알 수 없는 계정 상태는 정상으로 추정하지 않는다.
- API 응답에 `seasonId`, `fetchedAt`, `squadFpp`, `duoFpp`가 추가되었다. 모델과 화면을 함께 배포하고 기존에 열어 둔 브라우저는 새로고침한다. 이 API는 경쟁전 전용이며 일반전/솔로 전적 UI는 별도 범위다.

## 구조와 요청 관리

`UserStat → usePlayerStats → rank API → pubgService → pubgStats`

- 모달 상태/취소/오류 처리를 Composable로, 계산과 캐시/요청 예산을 서버 유틸리티로 분리했다. 오류를 잡아 `null`을 반환하던 `pubgApi` 래퍼는 제거했다.
- 성공 결과는 플랫폼+대소문자를 보존한 닉네임 기준으로 5분 캐시한다. 없는 플레이어/전적(404)은 30초만 캐시한다. 그 외 실패는 성공 데이터처럼 저장하지 않는다.
- 같은 요청은 진행 중인 Promise를 공유한다. 결과/오류 캐시 합계는 최대 200개, 진행 중인 서로 다른 조회는 최대 10개다.
- 현재 시즌 ID는 플랫폼별 1시간 캐시하고 동시 조회를 합친다. 시즌 전환 직후에는 시즌 캐시와 결과 캐시의 영향으로 이전 시즌이 잠시 표시될 수 있다.
- 기존 SDK의 대기 큐 대신 서버 인스턴스당 PUBG 실제 HTTP 요청을 최대 10회/60초로 제한한다. 초과 시 즉시 429와 `Retry-After`를 반환한다. SDK의 별도 큐/캐시는 끄고 이 서비스에서 관리한다.
- PUBG 자체 429도 안전한 메시지로 변환하고 잠시 새 조회를 억제한다. 이미 캐시된 성공 응답은 이때도 사용할 수 있다.
- 각 PUBG HTTP 요청의 타임아웃은 5초다. 클라이언트는 20초 제한과 자동 재시도 없음으로 설정했다. 최초 조회는 플레이어/시즌/경쟁전의 최대 3회 외부 요청, 시즌 캐시가 있으면 2회다.
- API 응답은 `Cache-Control: no-store`이며 위 캐시는 서버 메모리 내부에서만 동작한다. SDK 예외/인증 헤더를 클라이언트 응답에 넣지 않는다.

## 사용자 화면

- 모달이 열릴 때만 조회한다. 중복 클릭을 합치고, 닉네임/플랫폼 변경·모달 닫기·컴포넌트 해제 시 취소하고 늦게 도착한 결과를 무시한다.
- 로딩/정상 기록/기록 없음/조회 실패를 구분하며 실패 시 재시도할 수 있다. 조회 시각과 최대 5분 캐시 안내를 표시한다.
- 최근 매치 URL이 없거나 안전한 HTTP(S) URL이 아니면 링크를 만들지 않는다. 닉네임은 검증/인코딩하고 새 탭에는 `noopener noreferrer`를 적용한다.

## 검증 및 배포

- 새 단위 테스트 16개: 계산/누락값/TPP·FPP 분리, 입력 검증, 오류 정제, 제한 및 만료, 캐시/동시 요청/크기 제한, 시즌 공유, 클라이언트 요청 취소와 재시도, 안전한 링크.
- 전체 자동 테스트 58개, 타입 검사·린트·프로덕션 빌드·HTTP smoke 13개·`git diff --check` 모두 통과했다. 기존 대형 클라이언트 번들 경고는 남아 있다.
- 브라우저는 Git에서 제외된 `.firebase/stage4-ui` 레이어에서 실제 SDK의 HTTP 전송만 모의 응답으로 바꿔 확인한다. 실제 API 키/운영 PUBG 요청/운영 Firestore 데이터는 사용하지 않는다. 모의 경로는 정상 앱 빌드에 포함되지 않는다.
- 로컬 브라우저에서 로딩, TPP/FPP 분리, 평균 딜량 321/450, 누락 값 표시, 빈 기록 안내, 오류 안내와 재조회 복구를 확인했다. 모의 HTTP 검사에서 404 및 429+`Retry-After: 60`, 응답의 비밀정보 비노출도 확인했다. 정상 빌드의 `/_stats-check`는 404이며, 테스트 서버와 브라우저 탭을 종료했다.
- 이번 단계는 실제 PUBG 응답으로 검증하지 않았다. 운영 배포 후 알려진 플레이어의 현재 시즌 기록과 비교 검증은 별도로 수행한다.
- 새 Firebase 규칙/인덱스/환경변수/의존성 추가가 없다. 기존 `PUBG_API_KEY` 설정을 그대로 사용한다. 커밋·푸시·운영 배포는 별도다.

## 제한 및 후속 작업

- **메모리 캐시와 요청 예산은 인스턴스 단위다.** Vercel 인스턴스가 늘거나 재시작하면 공유되지 않는다. 여러 인스턴스 전체의 API 키 한도나 사용자별 악용 방지를 완전히 보장하지 않는다. 트래픽이 늘면 공유 저장소/배포 플랫폼의 요청 제한과 실제 PUBG 키 한도를 함께 검토해야 한다.
- SDK/공식 API 응답에 없는 경쟁전 항목을 표시하기 위해 일반전 데이터를 섞지 않는다. 향후 SDK 타입 보강이나 API 응답 변경이 있으면 매핑 테스트를 먼저 갱신한다.
- 2단계 자동 방 정리 활성화, 운영 실제 계정 검증, 5단계 모바일 화면, 6단계 목록/채팅 페이지 처리와 배포 자동 검사는 별도 작업이다.
